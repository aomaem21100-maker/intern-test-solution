# DECISIONS — บันทึกการตัดสินใจ

## D1: จะเก็บข้อมูลผู้ใช้ที่ Login ไว้ที่ไหน
- ทางเลือกที่คิดไว้: (A) React Context (B) Redux (C) ส่ง props ผ่านทุก component
- เลือก: A — React Context
- เพราะ: ข้อมูล user และ token ต้องใช้ร่วมกันในหลายหน้า และเปลี่ยนหลัก ๆ ตอน Login/Logout จึงใช้ Context ได้โดยไม่ต้องติดตั้ง state library เพิ่ม
- ข้อเสียของ A ที่ยอมรับ: เมื่อ Context เปลี่ยน component ที่ subscribe อาจ render ใหม่ หาก state โตขึ้นหรือซับซ้อนขึ้นค่อยพิจารณา Zustand/Redux

## D2: จะจัดการ route และสิทธิ์เข้าหน้าอย่างไร
- ทางเลือกที่คิดไว้: (A) ตรวจ role แยกในแต่ละหน้า (B) ใช้ ProtectedRoute ครอบ route (C) ซ่อนเมนูอย่างเดียว
- เลือก: B — ใช้ ProtectedRoute ตรวจ login และ role ก่อน render หน้า
- เพราะ: รวมกฎการเข้าถึงไว้จุดเดียว ลดโอกาสที่หน้าใดหน้าหนึ่งลืมตรวจ role และ redirect ผู้ใช้ไปหน้าที่เหมาะสม
- ข้อเสียของ B ที่ยอมรับ: ต้องกำหนด role ให้ route ถูกต้อง และเป็นเพียงการป้องกันใน frontend; ระบบจริงต้องตรวจสิทธิ์ซ้ำที่ backend ทุก endpoint

## D3: จะออกแบบความสัมพันธ์ Task กับผู้ใช้และ Project อย่างไร
- ทางเลือกที่คิดไว้: (A) เก็บชื่อผู้รับผิดชอบเป็นข้อความใน tasks (B) เก็บ assigned_to เป็น FK ไป users และ project_id เป็น FK ไป projects (C) เก็บข้อมูลทั้งหมดเป็น JSON
- เลือก: B — ใช้ Foreign Key
- เพราะ: ป้องกันการอ้างอิงผู้ใช้/โครงการที่ไม่มีอยู่จริง และ query Task ตามผู้รับผิดชอบหรือโครงการได้ชัดเจน
- ข้อเสียของ B ที่ยอมรับ: ต้องจัดการการลบ/เปลี่ยนผู้ใช้และโครงการตาม FK และการ join อาจเพิ่มความซับซ้อนของ query

## D4: Mock API ในส่วนที่ 3 จะจำลองการทำงานอย่างไร
- ทางเลือกที่คิดไว้: (A) เปลี่ยน state ทันทีโดยไม่หน่วงเวลา (B) ใช้ Promise กับ setTimeout (C) ทำ backend จริง
- เลือก: B — Promise + setTimeout
- เพราะ: โจทย์กำหนดให้จำลอง API และต้องแสดง loading state วิธีนี้ทำให้เห็นพฤติกรรม asynchronous โดยไม่ต้องสร้าง backend
- ข้อเสียของ B ที่ยอมรับ: ข้อมูลอยู่ใน memory ไม่ถาวร และไม่สามารถทดสอบปัญหาเครือข่าย/ฐานข้อมูลจริงได้

## D5: เมื่อ Employee กด Done จะอัปเดตหน้าจออย่างไร
- ทางเลือกที่คิดไว้: (A) รอ API สำเร็จแล้วค่อยเปลี่ยน UI (B) optimistic update แล้ว rollback เมื่อ error
- เลือก: B — optimistic update พร้อม rollback
- เพราะ: ผู้ใช้เห็นผลทันทีตามโจทย์ แต่หาก API จำลองล้มเหลวจะคืนค่าเดิม ไม่แสดงสถานะที่ server ไม่ได้บันทึก
- ข้อเสียของ B ที่ยอมรับ: ต้องเก็บสถานะเดิมเพื่อ rollback และต้องระวังคำขอหลายรายการที่เกิดพร้อมกัน

## การใช้ AI
ใช้ AI ช่วยร่างโครงสร้างเอกสาร ตรวจทานแนวคิดการออกแบบ และช่วยชี้จุดที่ควรตรวจในโค้ด จากนั้นต้องอ่านและทดสอบโค้ดทุกส่วนด้วยตนเองก่อนส่ง
